### 0-3. 採用方式の結論（先に結論だけ）

| 論点 | 採用 | 主な理由 |
| --- | --- | --- |
| レンダラー | **WebGLRenderer** | 安定性・`onBeforeCompile` によるシェーダー差し込みが使える・モバイル互換性 |
| 惑星の表現 | **カーブドワールド・シェーダー（擬似球面）** | 見た目の惑星半径と 400m のコース長を独立して調整できる |
| 見た目の惑星半径 | **R = 150m（100〜200m で調整可能な定数）** | 地平線 約22m・木の頭が約70m先から昇ってくる。森の奥行きと小惑星感を両立 |
| 無限ループ | **円環座標（s ∈ [0, 400)）+ 相対距離の折り返し描画** | 座標リセットの瞬間が存在せず、継ぎ目が原理的に生じない |
| 配置 | **seed 付き手続き生成（周期的な乱数・ノイズ）** | 同じ場所に常に同じ物。0m と 400m が数学的に連続 |
| 木の描画 | **InstancedMesh（モデル種別ごと）+ チャンク単位の可視ウィンドウ更新** | Draw Call を 1 桁〜数十に抑える |
| 影 | **リアルタイム影は使わない**（ブロブ影 + 頂点 AO + 木漏れ日模様） | 曲面シェーダーとの相性・コスト |
| ポストプロセス | **three/addons の EffectComposer + UnrealBloomPass + OutputPass** | 追加依存なし。HDR 輝度しきい値でオーブだけ光らせる |
| モーダル | **`<dialog>` 要素 + CustomEvent 連携** | フォーカストラップ・Esc・背面の inert をブラウザ標準で得られる |
| Astro 連携 | **カスタム要素 `<forest-experience>`** | Astro 推奨パターン。`disconnectedCallback` で確実に破棄できる |
| 追加依存 | `three`、`@types/three`（devDependencies）のみ | 要件「必要以上に外部ライブラリを追加しない」 |

### 設計の中心アイデア

1. **カメラは原点付近から動かない。世界の方を「カメラから見た相対座標」で描く**
   - すべてのオブジェクトは「コース座標 `(x, s)`」（s = コースに沿った距離 0〜400m）で定義する
   - 毎フレーム、カメラのコース位置 `cameraS` を uniform で渡し、頂点シェーダーで
     「カメラから見た相対距離 → 折り返し（±200m）→ 球面へ曲げる」を行う
2. **「進んだ距離」は無限に増える実数、「描画位置」は 400m で折り返す**
   - `totalDistance` は決してリセットしない。`% 400` は描画時の相対距離計算にだけ使う
   - そのため「400m → 0m へワープする瞬間」がそもそも存在しない
3. **惑星の見た目の半径 R と、コース長 L は独立したパラメータ**

## 2. Astro と Three.js の連携方法

### 2-1. 採用: カスタム要素

```astro
<!-- src/components/ForestExperience.astro（イメージ） -->
<forest-experience data-quality="auto">
  <canvas aria-hidden="true"></canvas>
  <noscript>このサイトの表示には JavaScript が必要です。</noscript>
</forest-experience>

<script>
  import { Experience } from "@/experience/Experience"

  class ForestExperienceElement extends HTMLElement {
    private experience: Experience | null = null
    connectedCallback() { this.experience = new Experience(this); void this.experience.start() }
    disconnectedCallback() { this.experience?.destroy(); this.experience = null }
  }
  if (!customElements.get("forest-experience")) customElements.define("forest-experience", ForestExperienceElement)
</script>
```

- `client:*` ディレクティブはフレームワーク用なので使わない。`<script>` はクライアントでのみ実行される
- `disconnectedCallback` がクリーンアップの唯一の入口になる。将来 `<ClientRouter />` を導入してもページ離脱時に破棄される
- `ClientRouter` は単一ページのため **導入しない**（ページ追加時に再検討）

### 2-2. 採用しない方式

| 方式 | 不採用理由 |
| --- | --- |
| `document.addEventListener("DOMContentLoaded")` で直接初期化 | 破棄タイミングを持てない。View Transitions 導入時に再実行されない |
| `is:inline` スクリプト | バンドル・TypeScript 処理が効かない |
| React Three Fiber / 島コンポーネント | 要件で除外 |

### 2-3. イベントリスナー管理

- Experience が 1 つの `AbortController` を持ち、すべての `addEventListener` に `{ signal }` を渡す
- `destroy()` で `abort()` → 全リスナーが一括解除される（解除漏れを構造的に防ぐ）

## 4. 3D 空間の座標設計

### 4-1. 3 種類の座標系

```
① コース座標（データ・生成の基準）
   s : コースに沿った距離 [0, L)  L = 400m   ← 円環。399.9 の次は 0
   x : 道の中心からの横方向距離（右が +）
   h : 地面からの高さ

② カメラ相対の平面座標（シェーダー内の中間表現）
   dz = wrap(s - cameraS)  ∈ [-L/2, L/2)   前方が「負の z」（Three.js の慣例）
   dx = x - cameraX

③ 描画座標（球面に曲げた後、Three.js のワールド座標）
   カメラ真下の地面 = 原点 (0, 0, 0)、上方向 = +Y、進行方向 = -Z
   惑星の中心 = (0, -R, 0)
```

### 4-2. 単位と主要定数（`world.constants.ts`）

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `COURSE_LENGTH` | 400 | 1 周の長さ（m）。1 単位 = 1m |
| `PLANET_RADIUS` | 150 | 見た目の惑星半径（m） |
| `EYE_HEIGHT` | 1.65 | 目の高さ |
| `PATH_HALF_WIDTH` | 1.2 | 道の半幅（道幅 2.4m） |
| `VISIBLE_AHEAD` | 100 | 前方の描画範囲 |
| `VISIBLE_BEHIND` | 30 | 後方の描画範囲（振り向かないが、側方視野の端のため少し残す） |
| `CHUNK_LENGTH` | 10 | 配置チャンクの長さ（400 を割り切れる値にする） |

`VISIBLE_AHEAD + VISIBLE_BEHIND (=130) < L/2 (=200)` を必ず守る。これにより
**同じオブジェクトが前方と後方に同時に見える** ことが起きない。

## 5. 球体の惑星表現の実装方法

### 5-1. 数学的検証（要件 13）

前提: 目の高さ h = 1.65m。地平線距離 `d_h = √(2Rh + h²) ≈ √(2Rh)`。
高さ H の物体の頭が見え始める距離 `d_v = √(2Rh) + √(2RH)`。距離 d での地面の落ち込み `≈ d² / 2R`。
地平線の見下ろし角（伏角）`α ≈ √(2h/R)`。

| 惑星半径 R | 地平線距離 | 高さ 8m の木が見え始める距離 | 30m 先の地面の落ち込み | 地平線の伏角 |
| --- | --- | --- | --- | --- |
| 63.7m（赤道 400m） | 14.5m | 46m | 7.1m | 約 13° |
| 100m | 18.2m | 58m | 4.5m | 約 10.4° |
| **150m（推奨）** | **22.2m** | **71m** | **3.0m** | **約 8.5°** |
| 200m | 25.7m | 82m | 2.3m | 約 7.4° |
| 300m | 31.5m | 101m | 1.5m | 約 6.0° |

考察:
- R = 63.7m では地面そのものが 14.5m 先で切れ、道の先が「崖の縁」のように見える。木も 46m 以内からしか現れないため **森の奥行きが出ない**。また地平線が視線より 13° 下にあり、画面の半分以上が空になる
- R = 150m なら、地面は 22m 先で丸く消え、木の頭は 70m 先から地平線の向こうに **せり上がって** くる。霧の終端（約 90m）と組み合わせて「奥深い森」と「丸い星」を両立できる
- R = 300m 以上では湾曲がほぼ平地にしか見えず、小惑星らしさが薄い

### 5-2. 3 方式の比較

| 方式 | 内容 | 長所 | 短所 | 判定 |
| --- | --- | --- | --- | --- |
| 1. 半径 63.7m の実球体 | 実際に Sphere を作り、カメラが球面を周回 | 物理的に正確。ループが自然に成立 | 半径がコース長で固定され、湾曲が強すぎる（上表）。カメラの姿勢計算が必要 | **不採用** |
| 2. 大きな球体上に 400m の周回コース | 例: R=150m の球の緯線（小円）上を周回 | 半径を自由にできる | 小円は測地線ではないため、道が常に一定方向へ曲がり続ける（旋回半径 約 70m）。地形・配置を球面座標で管理する必要があり複雑 | **不採用** |
| 3. 擬似球面（カーブドワールド・シェーダー） | 平面上のコースを、カメラ中心で頂点シェーダーにより球面へ曲げる | R と L が独立。ループは円環座標で継ぎ目なし。カメラ姿勢が常に単純 | 「1 周 400m なのに半径 150m」という数学的な矛盾があるが、見える範囲（±100m）では知覚不能。Raycast 用に CPU 側でも同じ変換が必要 | **採用** |

方式 3 は、どうぶつの森などで使われる手法と同系統。「見える範囲だけ正しく球に見えれば良い」という割り切り。

### 5-3. 曲げ変換（正確な球面写像）

近似の放物線 `y -= d²/2R` ではなく、要件 17-A の `angle = distance / radius` を使った **正確な球面写像** を採用する（横方向の湾曲や木の傾きも正しくなる）。

```
入力: カメラ相対の平面座標 (dx, h, dz)   h = 地面からの高さ
r      = √(dx² + dz²)          // カメラ真下からの地表距離（弧長）
θ      = r / R                  // 惑星中心から見た角度
dir    = (dx, dz) / r           // 水平方向の単位ベクトル（r=0 なら 0）
rr     = R + h                  // 惑星中心からの距離
出力:
  x' = dir.x * rr * sin θ
  z' = dir.z * rr * sin θ
  y' = rr * cos θ - R
法線: dir と上方向が張る平面内で θ だけ回転させる（ライティングを正しくするため）
```

- 木の頂点は高さ h ごとに同じ θ で外側に倒れるので、**遠くの木ほど向こう側に傾きながら沈む**（球面上で放射状に立つのと同じ）
- この関数は GLSL（`curvature.glsl`）と TypeScript（`curvature.utils.ts`）の **両方に同じ式で実装** する。TS 版はオーブの位置計算と Raycast に使う。両者の一致を目視確認するデバッグ表示を Phase 5 で用意する

### 5-4. シェーダーへの差し込み

- 対象マテリアル（`MeshStandardMaterial` / `MeshLambertMaterial`）に `onBeforeCompile` で以下を差し込むヘルパー `applyCurvature(material)` を作る
  - `#include <begin_vertex>` の後: インスタンス行列の平行移動成分（コース座標）から `dz` を求めて折り返し、頂点を球面へ写像
  - `#include <beginnormal_vertex>` の後: 法線を回転
- uniform は全マテリアルで **同じオブジェクトを共有**（`uCameraCourse: vec2(cameraX, cameraS mod L)`、`uPlanetRadius`、`uCourseLength`）。毎フレーム 1 回更新するだけで全体に反映される
- `customProgramCacheKey` を設定してプログラムキャッシュの衝突を防ぐ
- 曲げた後に Three.js 標準の `project_vertex` / fog 計算が走るため、**Fog は曲げ後の距離で正しく効く**
- シェーダーで頂点を動かすため、該当メッシュは `frustumCulled = false`。代わりにチャンク単位の CPU カリング（§10）で描画数を絞る

## 6. 400m 無限ループの実装方法

### 6-1. 方式比較

| 方式 | 内容 | 評価 |
| --- | --- | --- |
| A. 一定距離で座標リセット（テレポート） | 400m で全オブジェクトとカメラを 0m に戻す | 境界前後の配置を完全一致させる必要があり、1 フレームのずれ・影・パーティクルの不連続が出やすい。**不採用** |
| B. オブジェクトプーリング（ランナーゲーム式） | 後ろに消えた物を前に再配置 | 再配置先の決定がランダムだと「同じ場所に同じ物」が保証されない。**単独では不採用**（考え方は §10 で利用） |
| C. 無限手続き生成（チャンク単位） | 絶対位置ごとに無限に生成 | ループ不要だが、要件の「400m を 1 周」「オーブのコンテンツが周回する」に合わない。**不採用**（細部のバリエーションとして将来オプション化は可） |
| D. 実際の円形・球面コース | 方式 1 の実球体 | §5 で不採用 |
| **E. 円環座標 + 相対距離の折り返し描画** | すべてを s ∈ [0,400) で定義し、描画時に `wrap(s - cameraS)` を計算 | 継ぎ目もリセットも存在しない。**採用** |

### 6-2. 仕組み（要件 17-B への回答）

`distance % 400` を **カメラ位置そのものに適用するのは不適切**（399.9 → 0.0 で値が飛ぶ）。
代わりに、**「カメラとオブジェクトの差」に対して折り返しを適用** する。

```ts
// 疑似コード
const L = 400
// -L/2 〜 +L/2 に折り返す。負数でも正しく動く mod を使う（JS の % は負数で負を返すため）
const wrapSigned = (value: number) => ((((value + L / 2) % L) + L) % L) - L / 2

totalDistance += step          // 無限に増える（リセットしない、後退で減ってもよい）
const cameraS = positiveMod(totalDistance, L)   // シェーダーに渡すのはこちら

// 各オブジェクト（GLSL 内でも同じ式）
const dz = wrapSigned(object.s - cameraS)
```

具体例: cameraS = 399m、木の s = 3m の場合

```
object.s - cameraS = 3 - 399 = -396
wrapSigned(-396) = +4     → 「4m 先の木」として描かれる
次のフレームで cameraS = 0.5（totalDistance = 400.5）
object.s - cameraS = 2.5 → 「2.5m 先の木」         ← 4m → 2.5m と連続している
```

カメラは一度もワープしていない。動いているのは `dz` だけで、その値は常に連続する。

### 6-3. ループ境界をユーザーに気づかせないための対策一覧

| # | 対策 | 対象 |
| --- | --- | --- |
| 1 | すべての配置を円環座標で定義し、描画時に折り返す（上記） | 全オブジェクト |
| 2 | 連続的な場（地面の起伏・道の蛇行・植生の密度）は **周期関数** で作る。<br>例: `sin(2π k s / L)`（k は整数）、ノイズは円に埋め込んだ座標 `(cos(2πs/L), sin(2πs/L)) * r` で 2D/3D ノイズを引く | Ground / Path / Forest |
| 3 | 地面テクスチャのタイルサイズは L を割り切る値（例: 4m → 100 タイル） | Ground |
| 4 | 乱数は「セル番号 mod セル数」から生成（§11）。境界をまたぐ距離判定も `wrapSigned` を使う | Forest |
| 5 | 光・霧・空はコース位置に依存させず、カメラ相対で一定にする | Atmosphere |
| 6 | 可視範囲 (130m) < L/2 (200m) を保証 | 定数 |
| 7 | 時間で変化する演出（浮遊粒子・オーブの揺れ・木漏れ日のゆらぎ）は経過時間ベースにし、位置に依存させない | 演出 |
| 8 | 目立つランドマーク（大岩・倒木）は 400m 内に複数種を分散し、1 周内で 1 回きりの特徴物を作らない | 配置ルール |

補足: オーブはコンテンツ（Orb 01〜N）が周回するため、2 周目で同じオーブに再会することは避けられない。これは「ループが分かる」というより「星を 1 周した」という体験として許容する（世界観上むしろ自然）。

## 7. スクロールと移動量の管理方法

### 7-1. 状態

```ts
interface IScrollState {
  targetDistance: number   // 入力で増減する目標位置（m）
  currentDistance: number  // 実際のカメラ位置（m）= totalDistance
  velocity: number         // 現在速度（m/s）。カメラ揺れ・演出に使う
  isEnabled: boolean       // モーダル表示中は false
}
```

### 7-2. 入力の正規化（wheel）

```ts
// deltaMode ごとに「ピクセル相当」へ揃える
const LINE_HEIGHT_PX = 16
deltaPx = deltaMode === 0 ? deltaY
        : deltaMode === 1 ? deltaY * LINE_HEIGHT_PX
        : deltaY * window.innerHeight     // 2 = ページ単位

deltaPx = clamp(deltaPx, -MAX_EVENT_DELTA_PX, MAX_EVENT_DELTA_PX)   // 1 イベントの暴走を抑止（120px）
targetDistance += deltaPx * WHEEL_METERS_PER_PX                     // 0.015 → マウス 1 ノッチ(≈100px) ≈ 1.5m
targetDistance = clamp(targetDistance, currentDistance - MAX_LEAD, currentDistance + MAX_LEAD)  // 先行量の上限 12m
```

- `wheel` リスナーは `{ passive: false }` で登録し `preventDefault()`（トラックパッドのバウンスや戻るジェスチャを抑止）
- トラックパッドは OS 側の慣性イベントが続くため、自前の慣性は控えめで足りる

### 7-3. フレームレート非依存の追従

```ts
// 指数減衰 lerp: dt に関係なく同じ時間で同じだけ近づく
const alpha = 1 - Math.exp(-DAMPING * dt)        // DAMPING = 4（大きいほどキビキビ）
let step = (targetDistance - currentDistance) * alpha
step = clamp(step, -MAX_SPEED * dt, MAX_SPEED * dt)   // MAX_SPEED = 8 m/s
currentDistance += step
velocity = step / dt
```

- `dt` は Ticker が `Math.min(dt, 0.1)` でクランプ（タブ復帰時の大ジャンプ防止）
- 入力を止めると `target - current` が指数的に縮み、自然に停止する（＝慣性）

### 7-4. タッチ・キーボード

| 入力 | 仕様 |
| --- | --- |
| タッチ（Pointer Events, `pointerType === "touch"`） | 縦ドラッグ量 × `TOUCH_METERS_PER_PX`（0.03）を target に加算。指を離した瞬間の速度 × `FLICK_TIME`（0.3s）を追加して慣性を付ける。canvas に `touch-action: none` |
| キーボード | `ArrowUp` / `W` / `PageDown` / `Space` で前進、`ArrowDown` / `S` / `PageUp` で後退（1 回 2m） |
| 後退 | 許可する（円環なのでどこまでも戻れる） |
| モーダル表示中 | `isEnabled = false` にし、`targetDistance = currentDistance` で残りの移動を打ち切る |
| `prefers-reduced-motion` | DAMPING を上げて慣性を短く、カメラ揺れを無効化 |

## 8. カメラ設計

### 8-1. パラメータ

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| 種類 | PerspectiveCamera | |
| 垂直 FOV | **55°**（16:9 で水平 約 87°） | 人の中心視野〜周辺視野の自然な範囲。60° を超えると広角歪みが目立つ |
| 縦長画面 | 水平 FOV が 60° を下回らないよう垂直 FOV を再計算（上限 75°） | スマホ縦持ちで左右の森が見切れないように |
| near / far | 0.1 / 150 | 霧の終端（90m）+ 余裕。near を小さくしすぎると深度精度が落ちる |
| 位置 | `(pathX(cameraS), EYE_HEIGHT, 0)` | 道の中央。カメラは Z 方向に動かない |
| 向き | 前方（-Z）から **下へ 4° ピッチ** | 地平線が伏角 8.5° 下にあるため、少し見下ろすと地平線が画面中央やや下に来て安定する |
| 上方向 | `(0, 1, 0)` 固定 | カメラ真下が常に球の「北極」なので、惑星中心→外向き = +Y が常に成り立つ |

### 8-2. 球面の上を歩く仕組み（要件 17-A への回答）

要件の `angle = distance / radius` + `sin / cos` は **正しい** 。違いは「誰を動かすか」だけ。

```
【案 1: カメラが球面を周回する（不採用）】          【案 2: カメラを北極に固定し、世界を回す（採用）】

         カメラ ●→ 接線方向に lookAt                          ● カメラ（常に頂上）
        ╱  up = normalize(pos - center)                    ___│___
      ╱        θ = distance / R                         ╱     ↓     ╲   ← 前方の物は θ だけ
    ●  中心                                             │  中心 ●     │      向こうへ回り込む
      ╲                                                  ╲___________╱
pos = center + R(0, cos θ, -sin θ)                   物体の相対角 θ = dz / R
forward = (0, -sin θ, -cos θ)                        pos' = (R+h)(sin θ·dir, cos θ) - (0,R,0)
camera.up.copy(up); camera.lookAt(pos + forward)
```

案 2 を採用する理由:
1. 惑星半径 R をコース長 L から独立させられる（案 1 は 2πR = L に縛られる）
2. カメラの姿勢計算が不要。`up` の更新漏れや lookAt の特異点が起きない
3. 座標値が常に原点付近に収まり、float32 の精度問題が起きない
4. ループ境界でカメラの値が飛ぶ問題が構造的に存在しない

### 8-3. 歩行感の演出（CameraController）

| 演出 | 実装 | 値 |
| --- | --- | --- |
| 上下揺れ（ヘッドボブ） | `phase = totalDistance / STEP_LENGTH * π`、`y += sin(phase) * amp * speedFactor` | STEP_LENGTH 0.7m、amp 0.025m |
| 左右揺れ | `x += sin(phase / 2) * 0.012 * speedFactor` | |
| speedFactor | `clamp(|velocity| / WALK_SPEED, 0, 1)` を平滑化 | WALK_SPEED 3m/s |
| マウス視差 | ポインタ位置で yaw / pitch を最大 ±2.5° 傾け、指数減衰で追従 | タッチ端末では無効 |
| 道の蛇行追従 | `yaw = atan(pathX'(cameraS))` | §9 の蛇行振幅が 0 なら無効 |

- 揺れは距離ベースなので、止まると揺れも止まる（時間ベースだと立ち止まっても揺れ続けて不自然）

## 9. 道の作り方

### 9-1. 地面メッシュ（Ground = Planet の役割）

- カメラに追従する **240m × 240m、120×120 分割（2m/頂点）の平面** を 1 枚だけ使う
- 頂点シェーダーで §5-3 の球面写像を適用 → 画面上は球冠（惑星の表面）になる
- カメラに追従させるだけなので、メッシュ自体はループの影響を受けない
- 地面を地平線（22m）より大きくする理由: **地平線の向こうにある木の根元を地面が隠す** 必要があるため（隠す地面がないと根元が透けて見える）

### 9-2. 道の表現（地面シェーダー内で描く）

- 道専用メッシュは作らず、地面のフラグメントシェーダーで **道マスク** を計算する（Draw Call 0 増加、Z ファイティングなし）
  - `d = |x - pathX(s)|`、`mask = 1 - smoothstep(PATH_HALF_WIDTH - 0.2, PATH_HALF_WIDTH + 0.3, d + noise(x, s) * 0.3)`
  - 土の色と草地の色を `mask` で混ぜる。縁のノイズでギザギザの自然な境界にする
- 地面の模様（草地・土・落ち葉）はコース座標 `(x, s)` でサンプリング。s 方向のタイルは L を割り切るサイズ
- 道の蛇行: `pathX(s) = A1·sin(2π·2s/L) + A2·sin(2π·5s/L + φ)`（整数倍の周波数なので s=0 と s=400 で必ず一致）。Phase 2 では振幅 0（直線）、Phase 7 で 1〜1.5m を試す
- 起伏: 道から離れるほど大きくなる低周波の周期ノイズで高さを足す（道の上は平坦に保つ）。木の根元の高さも同じ関数で求める

## 10. 木・岩・植物の配置方法（数百本の木をどう描くか）

### 10-1. 描画方式の比較

| 方式 | Draw Call | 評価 |
| --- | --- | --- |
| Mesh を木の数だけ作る | 本数 × マテリアル数（数千） | **不採用** |
| ジオメトリを 1 つにマージ | 1 | 個別の再配置ができず、ループ・カリングと相性が悪い。**不採用** |
| BatchedMesh | 1 | 異なる形状を 1 回で描けるが API が複雑。現段階では過剰。**不採用（将来候補）** |
| **InstancedMesh（モデル種別 × マテリアルごとに 1 つ）** | 種別数 × 2 程度 | **採用** |

### 10-2. 構成

```
木 3 種類 × (幹, 葉) = 6 InstancedMesh
岩 2 種類              = 2
倒木 1 種類            = 1
低木・シダ 2 種類       = 2
草（板ポリ）            = 1
ブロブ影               = 1
------------------------------
合計 13 Draw Call 程度（地面・空・オーブ・ポストプロセスを含めても 30 前後）
```

### 10-3. チャンク単位の可視ウィンドウ（プーリング）

```
コース全体（400m = 40 チャンク × 10m）の配置データを起動時に一度だけ生成し、
チャンク番号ごとの配列に保持する（CPU メモリのみ、軽い）

カメラが新しいチャンクに入ったときだけ:
  可視チャンク = [cameraChunk - 3, cameraChunk + 10] を mod 40 で列挙（約 13 チャンク）
  各 InstancedMesh のバッファへ、可視チャンクの配置を詰め直す
    instanceMatrix ← (x, h, s, 回転, スケール)   ※ s はコース座標のまま
  mesh.count = 詰めた数
  instanceMatrix.needsUpdate = true

毎フレームは uniform（cameraS）を更新するだけ。移動・折り返し・湾曲はシェーダーが行う
```

- 再構築は 10m ごと（8m/s でも 1 秒あたり 1 回未満）で、1 回あたり数百行列の書き込み → 負荷は無視できる
- バッファ容量は「可視チャンク内の最大本数」で確保し、以後は再確保しない
- 可視範囲外のチャンクは GPU に送らないため、これが実質的な **フラスタム / 距離カリング** になる

### 10-4. 本数と負荷の目安

| 種類 | 1 周あたり | 同時描画 | 1 体のポリゴン | 同時描画ポリゴン |
| --- | --- | --- | --- | --- |
| 木 | 約 1,000 | 約 330 | 800〜1,500 | 約 40 万（PC） |
| 岩・倒木 | 約 300 | 約 100 | 200〜500 | 約 4 万 |
| 低木 | 約 800 | 約 260 | 100〜300 | 約 6 万 |
| 草 | カメラ周辺 30m のみ | 約 3,000 | 4〜8 | 約 2 万 |

モバイルは木の密度係数 0.5、草を 1/3 にして約 20 万ポリゴン以下を目標にする。

### 10-5. LOD

- 霧と地平線で 70〜90m 以遠は見えないため、`THREE.LOD`（オブジェクト単位で InstancedMesh と非互換）は **使わない**
- 代わりに 2 層構成: 近景（〜40m）の帯は通常の木、**遠景の帯（40〜90m 横）は板ポリの木シルエット** にして奥行きの密度を安く出す（Phase 8 で必要なら）

## 11. Procedural Generation の設計

### 11-1. 採用判断

**採用する**。手配置では 400m × 両側の数千オブジェクトを管理できず、さらに「同じ場所に常に同じ物」「境界の連続」を保証するには決定的な生成が最も確実なため。
ただし **完全なランダムではなく、ルール + seed 付き乱数 + 密度関数** で制御する。

### 11-2. seed 付き乱数

```ts
// mulberry32: 32bit 状態の軽量 PRNG。同じ seed なら必ず同じ列を返す
// hash2(cellX, cellS, seed): セル座標から seed を作る整数ハッシュ
const cellSeed = hash2(cellX, cellS % CELL_COUNT_S, WORLD_SEED)   // ← mod で円環を保証
const random = mulberry32(cellSeed)
```

- セル番号を `mod` で折り返すため、0m 付近と 400m 付近は **同じセル列の連続** になる
- `WORLD_SEED` を変えると別の森になる（デバッグ GUI から切り替え可能にする）

### 11-3. 配置アルゴリズム（ジッター付きグリッド + 密度関数）

```
for 各セル (cellX, cellS)   ※ セルサイズは種類ごと（木 3m×3m、岩 6m×6m など）
  center = セル中心 + random ジッター（セルサイズの ±40%）
  x, s = center
  dist = |x - pathX(s)|                         // 道の中心からの距離

  // 除外ルール
  if dist < PATH_HALF_WIDTH + 種類別マージン → skip   // 木 2.0m、低木 0.6m、草 0.2m
  if オーブの周囲（s ± 3m, dist < 3m）→ skip           // オーブを遮らない
  if dist > 種類別の最大距離 → skip                    // 木 45m

  // 密度ルール（確率で間引く）
  density = 帯ごとの基本密度(dist) × 周期ノイズ(x, s)   // 林の濃淡・空き地を作る
  if random() > density → skip

  // 個体差
  variant  = 重み付き抽選（木 A/B/C）
  rotY     = random() * 2π
  scale    = lerp(0.8, 1.3, random())
  tilt     = (random() - 0.5) * 6°                     // わずかな傾き
  h        = groundHeight(x, s)                        // 地面の起伏に合わせる
  → chunks[floor(s / CHUNK_LENGTH)].push(...)
```

| 帯（道の中心から） | 内容 |
| --- | --- |
| 0〜1.2m | 道（何も置かない。落ち葉テクスチャのみ） |
| 1.2〜3.5m | 草・小さな植物・小石（低い物だけ、視界を塞がない） |
| 3.5〜12m | まばらな木・低木・岩・倒木（道に沿った「縁」） |
| 12〜45m | 密な木（森の壁） |

## 12. オーブの配置方法

- コンテンツ数 N から等間隔に配置: `s_i = (i + 0.5) * L / N`
  - N = 10 → 40m 間隔、N = 20 → 20m 間隔。要件（20〜40m）に収まるよう **N は 10〜20 を推奨**。範囲外なら開発時に `console.warn`
- 横位置: 道の中央付近だが、カメラが突き抜けないよう `x = pathX(s) ± 0.8m`（左右交互）
- 高さ: 地面から 1.2m（目線より少し下）
- アニメーション: 上下 ±0.12m（周期 3s）、Y 軸回転 0.4 rad/s、各オーブで位相をずらす
- 見た目: 半径 0.25m の球 + HDR 発光色（§16）+ 周囲に少数の光の粒（Points）
- 近接時: 距離 1.5m 以内ではスケールを縮めてカメラとの交差を防ぐ
- **オーブは数が少ない（10〜20 個）ため InstancedMesh にせず個別の Mesh** にする。位置は §5-3 の TS 版変換で毎フレーム CPU 計算する（シェーダーで曲げない）→ 通常の Raycaster がそのまま使える
- 可視範囲外（dz が §4 の範囲外）のオーブは `visible = false`

## 13. オーブのクリック判定

```
pointerdown: 押下位置と時刻を記録
pointerup  : 移動 < 6px かつ 押下時間 < 400ms のときだけ「クリック」とみなす
             （タッチのスワイプ移動を誤ってクリック扱いしない）
  → NDC 座標を計算 → raycaster.setFromCamera
  → 判定対象は「表示中のオーブのヒット判定用球（半径 0.5m、非表示）」のみ
  → 交差あり かつ 距離 < 40m なら dispatch "forest:orb-select" { orbId }
pointermove: 1 フレームに 1 回だけ（rAF 内で）ホバー判定 → cursor: pointer 切り替え・オーブを少し明るく
```

- ヒット判定用の球を見た目より大きくすることで、小さなオーブもクリックしやすくする
- 木の InstancedMesh は判定対象に含めない（シェーダー変形後の形を CPU は知らないため、また遮蔽判定が不要なため）

## 14. Astro のモーダルとの連携

### 14-1. イベント設計（ブラウザ標準の CustomEvent）

| イベント名 | 発火元 → 受信側 | detail | 用途 |
| --- | --- | --- | --- |
| `forest:orb-select` | OrbManager / OrbList → OrbModal | `{ orbId: TOrbId }` | オーブが選ばれた |
| `forest:modal-change` | OrbModal → Experience | `{ isOpen: boolean, orbId: TOrbId \| null }` | 移動の停止・再開、背景の減光 |

- すべて `window` に dispatch する
- `declare global { interface WindowEventMap { ... } }` で型を拡張し、`addEventListener` の引数が型安全になるようにする
- 発火用ヘルパー `dispatchOrbSelect(orbId)` 等を `orb.events.ts` に集約（イベント名の文字列直書きを防ぐ）
- 停止の起点を「モーダルの開閉」に一本化することで、クリック以外（OrbList のボタン等）から開いた場合も同じく停止する

### 14-2. OrbModal.astro

- `<dialog>` + `showModal()` を使う
  - フォーカストラップ・`Esc` で閉じる・背面の `inert` 化・閉じた後に元の要素へフォーカス復帰をブラウザが行う
  - `::backdrop` で背景を少し暗く（`rgb(0 0 0 / 0.35)` + 軽い `backdrop-filter: blur(2px)`）
- コンテンツは **ビルド時に Astro が `<template data-orb-id="orb-01">` として全件出力** し、クライアントは id で複製して差し込むだけ
  - 画像は `astro:assets` の `<Image />` で最適化（サイズ・形式・`width/height` 属性によるレイアウトシフト防止）
  - テキストが HTML に存在するので、JS なしでもクロール・翻訳が可能
- アクセシビリティ:
  - `aria-labelledby`（タイトル）、`aria-describedby`（本文）
  - Close ボタンは `<button type="button">` + `aria-label="閉じる"`、開いたときの初期フォーカスは Close ボタン
  - 背景クリック（dialog 自身がターゲット）で閉じる
  - 開閉アニメーションは `prefers-reduced-motion` で無効化

### 14-3. OrbList.astro（キーボード・スクリーンリーダー用）

- canvas 内のオーブはキーボードで選べないため、**オーブ一覧のボタン群** を視覚的に隠して（フォーカス時のみ表示）配置する
- 各ボタンは `forest:orb-select` を発火 → 同じモーダルが開く
- canvas には `aria-hidden="true"` を付け、ページの説明は見出し（視覚的に非表示）で提供する

## 15. Lighting / Fog / Shadow 設計

| 要素 | 判定 | 設定案 |
| --- | --- | --- |
| HemisphereLight | **使う**（AmbientLight の代わり） | 空色 `#9fc7c0` / 地面色 `#2b3a2a` / 強度 1.2。上下で色が違うので「森の中の環境光」らしくなる |
| DirectionalLight | **使う**（影なし） | 暖色 `#ffe2b0`、強度 2.0、斜め前方の低い角度。カメラ相対で固定（どこへ進んでも同じ光 = ループに強い） |
| AmbientLight | 使わない | Hemisphere で代替 |
| PointLight（オーブ） | 原則使わない | ライト数に比例してシェーダーが重くなる。必要なら「最寄りのオーブ 1 個」だけに 1 灯を付け替える（Phase 7 で検討） |
| Fog | **使う** | 線形 `THREE.Fog(color, 20, 90)`。色は空の地平線付近の色と **完全一致** させる（地面の端・木の出現を溶かす） |
| 空 | **使う** | カメラ追従の大きな球に、上→地平線のグラデーションを描く ShaderMaterial（`fog: false`、`depthWrite: false`）。下端色 = Fog 色 |
| リアルタイム影（shadowMap） | **使わない** | 曲面シェーダーでは影用の深度マテリアル（`customDepthMaterial`）にも同じ変形が必要。数百本のキャスターとカメラ追従でコスト大 |
| 影の代替 | **使う** | ① 木・岩の根元に放射グラデーションのブロブ影（InstancedMesh の板ポリ、乗算合成）② GLB の頂点カラー / テクスチャに AO を焼き込む ③ 地面シェーダーに木漏れ日の模様（低周波ノイズを時間でゆっくり揺らす） |
| 木漏れ日の光の筋 | **使う** | 加算合成の縦長の板ポリ（光芒カード）を周期的に配置し、カメラ方向へビルボード。体積レンダリングは使わない |
| 浮遊する粒子 | **使う** | Points で光る埃・胞子を数百個。カメラ周辺の箱に閉じ込めて循環させる（位置に依存しないのでループと無関係） |
| Tone Mapping | **使う** | `ACESFilmicToneMapping`、exposure 1.0 前後。色味が強すぎる場合は `AgXToneMapping` と比較（GUI で切り替え） |
| Color Management | **使う（既定のまま）** | `outputColorSpace = SRGBColorSpace`。カラーテクスチャは `SRGBColorSpace`、法線・ラフネス等は `NoColorSpace` |

## 16. Bloom などの Post Processing

| 項目 | 判定 | 内容 |
| --- | --- | --- |
| Bloom | **使う（PC）** | `UnrealBloomPass`（threshold 1.0、strength 0.8、radius 0.4 を起点に調整） |
| 選択的 Bloom の方法 | **輝度しきい値方式** | EffectComposer は HDR（HalfFloat）で描くため、オーブの発光色だけを 1.0 を超える値（例: 色 × 4）にすれば、暗い森は光らずオーブだけが光る。レイヤーを分けた 2 パス方式（selective bloom）より単純で軽い |
| OutputPass | **使う** | Composer 使用時はここでトーンマッピングと sRGB 変換を行う |
| アンチエイリアス | **使う（PC）** | Composer のレンダーターゲットで MSAA（samples: 4）。モバイルは 0 |
| モバイルの Bloom | 品質 low では **無効** | 代替としてオーブに加算合成のグロー用スプライトを重ねる |
| 被写界深度 / SSAO / モーションブラー / God Rays パス | **使わない** | 負荷に対して得られる効果が小さい。光芒は §15 の板ポリで代替 |
| ビネット / 色調補正 | **任意（Phase 7）** | 必要なら OutputPass 前に軽量な ShaderPass 1 枚にまとめる |

## 17. パフォーマンス最適化

### 17-1. 採用 / 不採用の整理

| 技術 | 判定 | このサイトでの使い方 |
| --- | --- | --- |
| Draw Call 削減 | **採用** | InstancedMesh・道を地面シェーダーに統合・マテリアル共有。目標 PC 60 / モバイル 40 以下 |
| InstancedMesh | **採用** | 木・岩・草・影 |
| LOD | **限定採用** | `THREE.LOD` は不使用。遠景はシルエット板ポリの帯で代替 |
| Texture 圧縮（KTX2 / Basis） | **採用（Phase 8）** | GPU メモリ削減の効果が最も大きい。`KTX2Loader` + transcoder を `public/basis/` に配置 |
| GLB | **採用** | 木・岩のモデル形式 |
| Draco | 不採用 | Meshopt を採用 |
| Meshopt | **採用（Phase 8）** | `EXT_meshopt_compression`。`MeshoptDecoder` は three/addons 同梱 |
| Object Pooling | **採用** | §10-3 のチャンク単位のインスタンスバッファ再利用 |
| Frustum Culling | **代替で採用** | シェーダー変形のため標準カリングは無効化し、チャンク単位の距離カリングで代替 |
| Shadow 最適化 | 影自体を不使用 | 将来使う場合は近距離のみ・1 灯・`PCFSoftShadowMap`・マップ 1024 |

### 17-2. その他の対策

- **Pixel Ratio**: `Math.min(devicePixelRatio, 2)`（PC）、`1.5`（モバイル）。さらに動的品質で下げる
- **動的品質調整**: 直近 2 秒の平均フレーム時間を監視し、22ms を超え続けたら段階的に下げる（pixelRatio → Bloom → 草の密度）。上げる方向には戻さない（品質の点滅を防ぐ）
- **GPU 負荷**: 葉は `transparent` ではなく `alphaTest`（並べ替え不要・深度書き込み可）。可能ならアルファを使わないローポリの塊状の葉にする（幻想的な絵柄とも合う）
- **requestAnimationFrame**: `renderer.setAnimationLoop` に一本化。`document.hidden` 中はループを止める。`dt` は 0.1s でクランプ
- **破棄**: Experience が生成したジオメトリ・マテリアル・テクスチャ・レンダーターゲットを登録する `disposables` 配列を持ち、`destroy()` で全件 `dispose()`。最後に `renderer.dispose()`、`composer.dispose()`、`abortController.abort()`、`ResizeObserver.disconnect()`
- **WebGL コンテキスト喪失**: `webglcontextlost` で `preventDefault()` しループ停止、`webglcontextrestored` で再初期化
- **シェーダーのコンパイル待ち**: 初回表示前に `renderer.compileAsync(scene, camera)` を呼び、歩き始めのカクつきを防ぐ

### 17-3. 目標値

| 指標 | PC | モバイル |
| --- | --- | --- |
| FPS | 60 | 30〜60 |
| Draw Call | ≤ 60 | ≤ 40 |
| 同時描画ポリゴン | ≤ 50 万 | ≤ 20 万 |
| テクスチャ（GPU） | ≤ 64MB | ≤ 32MB |
| 初回ダウンロード（アセット合計） | ≤ 8MB | ≤ 5MB |

## 22. 状態管理方法

状態管理ライブラリは **導入しない**。状態の持ち主を明確に分ける。

| 状態 | 持ち主 | 他との共有方法 |
| --- | --- | --- |
| 進行距離・速度・入力の有効/無効 | ScrollController | Experience が毎フレーム読み取り、CameraController / World へ引数で渡す |
| カメラ姿勢・揺れ | CameraController | 内部のみ |
| 曲げ用の uniform（cameraS 等） | `applyCurvature.ts` の共有 uniform オブジェクト | Experience が毎フレーム 1 回更新 |
| 可視チャンク・インスタンスバッファ | Forest | 内部のみ |
| ホバー中のオーブ | OrbManager | 内部のみ |
| 品質 tier | Experience（`IQualitySettings`） | 生成時に各クラスへ引数で渡す |
| モーダルの開閉・表示中の orbId | `<dialog>` 自身（`open` 属性） | CustomEvent（§14） |

- 更新は「Experience の `update(dt)` が上から順に呼ぶ」一方向の流れにし、クラス同士が互いを直接参照しない
  `Ticker → ScrollController.update → CameraController.update → curvatureUniforms 更新 → World.update（Forest / Orb / Atmosphere）→ PostProcessing.render`

## 23. 実装する順番（ロードマップ）

各 Phase の終わりに `pnpm check` / `pnpm build` / `pnpm format:check` を実行し、ブラウザで動作確認する。
Phase ごとに作業ブランチ（例: `feat/phase-1-planet-walk`）を切り、`develop` に直接コミットしない。

### Phase 1: 最小構成でカメラが球面上をスクロール移動する

- 実装内容
  - `three` / `@types/three` を追加、`tsconfig.json` に `@/*` エイリアス
  - `index.astro` を全画面レイアウトに置き換え、`ForestExperience.astro`（カスタム要素）
  - `Experience` / `Viewport` / `Ticker`、`AbortController` によるリスナー管理、`destroy()`
  - `ScrollController`（wheel の正規化・lerp・最大速度、タッチ、キーボード）
  - `curvature.utils.ts` / `applyCurvature.ts` / `curvature.glsl`
  - 仮の地面: グリッド模様の平面 + 一定間隔のポール（コース座標で 10m ごと、0m だけ赤）
- 確認ポイント
  - ホイール・トラックパッド・タッチで前進 / 後退し、離すと滑らかに止まる
  - マウスとトラックパッドで速度感が大きく変わらない
  - ポールが地平線の向こうから「せり上がって」現れ、後方へ沈んでいく
  - 60fps と 144Hz モニタで同じ速度で進む（DevTools の CPU スロットリングでも確認）
  - リサイズ・DPR 変更に追従、ページの縦スクロールが発生しない
  - デバッグ GUI で `PLANET_RADIUS` を 63.7 / 150 / 300 に切り替えて見比べ、最終値を決める

### Phase 2: 道と地面を追加

- 実装内容: `Ground.ts`（地面シェーダー・道マスク・周期起伏）、`Atmosphere.ts` の最小版（Hemisphere + Directional + Fog + 空グラデーション）、`path.utils.ts`
- 確認ポイント
  - 道の縁が自然なギザギザで、道の上は平坦
  - 地面の端が見えず、地平線が霧と空に溶けている
  - 地面テクスチャがスクロールに合わせて正しい速度で流れる（滑って見えない）

### Phase 3: 木・岩を配置

- 実装内容: `random.utils.ts` / `noise.utils.ts` / `placement.utils.ts`、`Forest.ts`（InstancedMesh + チャンク更新）、まずはプリミティブ形状（円錐 + 円柱の木、二十面体の岩）で実装し、`AssetManager` 経由で GLB に差し替えられるようにする
- 確認ポイント
  - 道の上に木がない、道沿いの帯ルールが守られている
  - リロードしても同じ場所に同じ木がある。seed を変えると森が変わる
  - 木の根元が地面に埋まらず浮かない（起伏と一致）
  - Draw Call 数（stats / `renderer.info`）が想定どおり

### Phase 4: 無限ループ

- 実装内容: 円環座標・`wrapSigned` を全要素に適用、チャンクの mod 列挙、周期ノイズ・タイル境界の検証、境界確認用のデバッグ表示（現在の s・ラップ回数）
  - ※ Phase 1〜3 の段階から座標は円環前提で書くため、ここでは「境界での検証と不具合修正」が中心
- 確認ポイント
  - s = 395〜5m 付近を前進・後退で往復し、地形・道・木・テクスチャに継ぎ目や飛びがない
  - 10 周以上連続で進んでも挙動が変わらない（数値誤差の蓄積がない）

## 付録 A. アセット（GLB）の制作ガイドライン

| 項目 | 指針 |
| --- | --- |
| ポリゴン数 | 木 800〜1,500 tris、岩 200〜500、低木 100〜300、草 4〜8 |
| 構造 | **1 モデル = 1 メッシュ（幹と葉で最大 2 マテリアル）**。InstancedMesh はマテリアルごとに 1 つ必要なため、Blender 側で結合しておく |
| 原点 | 根元の中心を原点（0,0,0）に。Y-up、スケール 1 = 1m、トランスフォーム適用済み |
| テクスチャ | 1 モデル 512〜1024px。複数種の木で 1 枚のアトラスを共有するとマテリアル共有で Draw Call が減る |
| 葉 | alpha 付き板ポリなら `alphaTest`。可能なら板ポリを使わないローポリ形状 + 頂点カラー（幻想的な絵柄に合い、最も軽い） |
| AO | 頂点カラーまたはテクスチャに焼き込む（リアルタイム影の代替） |
| 圧縮 | `gltf-transform` で `meshopt` + `ktx2`（カラーは ETC1S、法線は UASTC） |
| 配置 | `public/models/`、`public/textures/`。パスは `assets.constants.ts` で一元管理 |
| モーダル用の写真・イラスト | 3D 用ではないため `src/assets/orbs/` に置き、`astro:assets` で最適化 |

## 付録 B. 決定済み・要確認事項

ここに挙げた前提で計画した。違う場合は承認時に指摘してほしい。

1. **惑星の見た目の半径は 150m を初期値** とし、Phase 1 で 63.7m / 300m と見比べて確定する
   - 2026-10-12 決定: Phase 1 で見比べた結果、デフォルメが効いた見た目を優先して **63.7m** を採用した。§5-1 の表のとおり地平線が近くなる（約 14.5m）ため、霧の距離や配置の可視範囲は Phase 2 以降でこの半径に合わせて調整する
2. **後退（逆スクロール）を許可** する
3. オーブのコンテンツは **10 件（40m 間隔）を仮データ** として作る
4. 3D モデルは当面 **プリミティブ形状で代用** し、GLB の用意は並行または後回しにする
5. 単一ページのため **`ClientRouter`（View Transitions）は導入しない**
6. 依存の追加は `three` と `@types/three` のみ（gltf-transform は必要時に `pnpm dlx` で一時利用）
7. 2026-10-12 決定: **1 周の長さ（COURSE_LENGTH）を 400m から 100m に変更** した（400m は長すぎるというユーザーの判断）。本書の 400m を前提にした数値は、次の制約に読み替える
   - 描画の折り返しは ±50m になる。§4-2 の「`VISIBLE_AHEAD + VISIBLE_BEHIND` < L/2」は「前方・後方とも 50m 未満」に読み替える（例: 前方 45m・後方 20m）
   - 地面メッシュは一辺 96m（±48m）にした。端の頂点が ±50m に達すると反対側へ飛んで地面が裂ける
   - 半径 63.7m では、高さ H の物の頭が見え始める距離は `14.5 + √(127.4·H)` m。これが 50m を超えると折り返し地点で突然現れるため、**配置物の高さは約 9.9m 未満** に抑える
   - 霧（FOG_NEAR 20 / FOG_FAR 90）は 50m より手前で消えるよう Phase 2 で見直す
   - 周期関数の周波数・テクスチャのタイル幅・チャンク長（10m）は 100 を割り切る値にする
   - オーブを 40m 間隔で 10 件置くと 1 周に収まらない。件数と間隔は Phase 5 でユーザーに確認する
8. 2026-10-12 決定（Phase 2）: 霧は **FOG_NEAR 8m / FOG_FAR 45m** にした（§15 の 20 / 90 から変更）。描画の折り返し（50m）より手前で完全に霧へ溶かすため
   - 空の球は地平線（伏角 約 13°）から仰角 3° までを霧の色にし、仰角 50° で天頂の色になるグラデーションにした
   - 地面の起伏は最大 1.2m（道の中心から 1.8m までは平坦）。配置物の高さの上限（約 9.9m）は起伏込みで考える
   - 道の縁は §9-2 の値より狭くした（`smoothstep(W-0.08, W+0.12, d + ずらし)`、ずらしは最大 0.25m）
   - 地面のシェーダーは §19 の `ground.vert.glsl / ground.frag.glsl`（全体を書く）ではなく、MeshLambertMaterial へのチャンク差し込み（`shaders/ground.glsl` / `ground.frag.glsl`）にした
9. 2026-10-13 決定（Phase 3）: **チャンク長（CHUNK_LENGTH）を 10m から 5m に変更** し、可視範囲は前方 9 チャンク・後方 2 チャンクにした（§10-3 の「cameraChunk - 3 〜 + 10」を読み替える）。10m だと新しく詰めたチャンクが 40m 先に入り、霧が溶けきらないため
   - 曲げ変換の折り返しは、頂点ごとではなく物の原点（メッシュ・インスタンスの原点）で決める。前方の端（50m 付近）の物の頂点が 1 周の両側へ裂けるのを防ぐため
   - 木のセルは 2.5m、岩のセルは 5m（どちらも 100 を割り切る）。配置する最大距離は 42m（地面メッシュの内側、霧の先）
   - 3D モデルは仮のプリミティブ形状（木 3 種・岩 2 種）。`IPropModel` の形で差し替えられる
