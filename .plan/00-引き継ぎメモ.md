  - `controls/ScrollController.ts`（wheel の正規化、指数減衰の追従、最大 8m/s、タッチのフリック、キーボード）、`controls/CameraController.ts`（FOV 55°、縦長画面での FOV 補正、4° の見下ろし）
  - `curvature/`: `curvature.glsl`、`applyCurvature.ts`（project_vertex を置き換え、法線も回転。`createCurvatureUniforms` で共有 uniform を作る）
  - `world/`: `World.ts`（仮の光・霧）、`Ground.ts`（カメラに追従する 240m の平面 + 仮のグリッド模様）、`CoursePoles.ts`（10m ごとの仮のポール。0m は赤）
  - `debug/Debug.ts`: `?debug` を付けたときだけ lil-gui / stats を動的 import する。惑星半径のプリセットとスライダー、進行距離を表示

計画との差分:

- 曲げ変換の共有 uniform は、モジュール単位のシングルトンにしなかった。`createCurvatureUniforms()` で Experience ごとに作り、引数で渡す（作り直しや破棄のときに状態が残らないようにするため）
- TS 版の球面写像と `wrapSigned` は、使い始める Phase 5（オーブ）で `curvature/curvature.utils.ts` として追加する。コース位置の折り返しには `MathUtils.euclideanModulo` を使う
- 共有 uniform とカメラのコース位置は World が持つ（`world.update(distance)`）。Experience は進行距離を渡すだけ
- `ScrollController` の入力の有効・無効の切り替え（`setEnabled`）は、使い始める Phase 6（モーダル）で追加する
- 平面ワールド座標は `x = コース x`、`y = 高さ`、`z = -s` で統一した。カメラの描画上の x は 0 に固定し、横方向は `uCurvatureCamera.x` で相対化する

## Phase 2 で作ったもの

- `procedural/path.constants.ts`（道の蛇行・起伏の定数）、`procedural/path.utils.ts`（TS 版の `pathX(s)` / `groundHeight(x, s)`）
- `shaders/ground.glsl`（GLSL 版の `groundPathX` / `groundHeight` / `groundNormal`。定数は Ground.ts が `material.defines` で TS から渡す）、`shaders/ground.frag.glsl`（周期 value noise・道のマスク・草地と土の色）
- `world/Ground.ts`: 仮のグリッドを地面シェーダーに置き換え。頂点を起伏で持ち上げ、法線も起伏に合わせる。メッシュは頂点間隔（2m）単位でカメラに追従させる
- `world/Atmosphere.ts` の最小版: Hemisphere + Directional + Fog + 空のグラデーション（`shaders/sky.vert.glsl` / `sky.frag.glsl`）。World から光と霧を移した
- 霧を `FOG_NEAR 8 / FOG_FAR 45` に変更（50m の折り返しより手前で完全に溶かす）。CAMERA_FAR は FOG_FAR + 60 = 105m
- デバッグ GUI に霧の near / far スライダーを追加
- 仮のポール（CoursePoles）の根元を `groundHeight` に合わせた

計画との差分（Phase 2）:

- 地面は計画書 §19 の `ground.vert.glsl / ground.frag.glsl`（シェーダー全体）ではなく、Phase 1 と同じく MeshLambertMaterial のチャンク差し込みにした。光・霧の計算を three.js 標準のまま使えるため
- 地面メッシュを頂点間隔単位で動かすようにした（連続的に動かすと頂点が起伏の上を滑り、丘の形が揺らいで見えるため）
- 道の縁は計画書 §9-2 の `smoothstep(W-0.2, W+0.3, …)` より狭く（`W-0.08`〜`W+0.12`、ずらし幅 0.25m）した。ぼやけて見えたため、見比べてギザギザがはっきりする値にした
- 起伏は最大 1.2m（道の中心から 1.8m までは平坦、12m で最大）。配置物の高さとの合計が約 9.9m 未満という制約に含めて考える
- シェーダーのコメントに `#include <...>` の文字列を書くと、チャンクの置換に巻き込まれてコンパイルエラーになる。コメントでは「common チャンク」のように書く
- コードレビュー後のリファクタリング:
  - 霧をカメラからの直線距離で掛けるようにした（`applyCurvature` が fog_vertex を置き換える）。ビューの奥行きのままだと、画面の端では 50m の折り返し地点が霧に溶けきらないため
  - チャンクへの差し込みを `shaders/shaderChunk.utils.ts` に共通化した
  - ノイズのハッシュを sin を使わない hash12 に変えた（大きな引数で精度が落ちるため）。模様の細部は変わった
  - ノイズのセル幅を Ground.ts の定数にして、COURSE_LENGTH を割り切るかをコンストラクタで検証するようにした。GLSL へ渡す数値は丸めない

計画との差分（Phase 3）:

- 曲げ変換の折り返しを、頂点ごとではなく物の原点（メッシュ・インスタンスの原点）で決めるように変えた（`curvature.glsl` の `curvatureRelative(flat, anchor)`）。頂点ごとだと、折り返し位置付近の木の頂点が 1 周の両側へ裂けるため
- チャンク長を 10m から **5m** に変えた（20 チャンク）。可視範囲は前方 9・後方 2 チャンク。10m だと新しいチャンクが 40m 先に現れ、霧が溶けきらず木がうっすら現れるため
- 木のセルは 3m ではなく 2.5m（100 を割り切る値）。木の帯は 3.5m から、配置する最大距離は 42m（地面メッシュの内側）
- 木の高さはモデル単体で最大 約 6.2m、拡大率 1.3 倍で 約 8.1m（起伏を足しても 9.9m 未満）
- 根元は 0.25m 埋める。地面メッシュと `groundHeight` の差は実測で最大 約 0.07m
- オーブの周囲の除外は Phase 5 で入れる（`placement.utils.ts` に TODO）
- コードレビュー後のリファクタリング:
  - 配置物の間に最小間隔（`clearance`: 木 0.6m・岩 0.9m の半径の合計）を設け、木同士・木と岩が重ならないようにした。木 → 岩の順に置き、後から置く物が避ける
  - 1 周の長さを割り切るかの検証を `world/course.utils.ts` の `assertDividesCourseLength` に共通化し、チャンク長・配置セル幅・空き地ノイズのセル幅も起動時に検証する。TS 版の折り返し `wrapSignedCourse` も同じファイルに置いた（Phase 5 のオーブでも使う）
  - Forest はインスタンス行列を生成時に一度だけ作り、詰め直しでは書き写すだけにした
  - 生成の途中で失敗したとき、Forest・World・Experience がそれまでに作った物（モデル・地面・レンダラー・リスナー）を破棄してから例外を投げる。seed の切り替えに失敗したときは元の森を残す

## Phase 3 の後の調整（鬱蒼とした森）

- ユーザーの要望で、木の葉を大きくし、森を密にした
  - 葉: 針葉樹の円錐の半径 1.8 / 1.4 / 1.0 → 2.4 / 1.9 / 1.4、広葉樹の樹冠の半径 1.7 → 2.4、細長い木の幅 0.9 → 1.2。全高は最大 約 6.5m（拡大率 1.3 倍で 約 8.45m、起伏を足して 約 9.65m）
  - 密度: 道の縁（3.5m）0.15 → 0.5、8m で 0.7、12m 以遠 0.7 → 0.9。空き地による間引き 0.75 → 0.5
  - 結果: 同時描画 約 3.5 万ポリゴン（以前は 約 2.6 万）、Draw Call は 10 のまま
- 木を道に近づける（最小距離 3.5m 未満）と、針葉樹の一番下の段が目の高さ（1.65m）近くまで張り出してカメラに当たるおそれがあるため、最小距離は 3.5m のまま

## フラクタルの木（Phase 3 の後の追加）

- ユーザーの要望で、木の枝をフラクタル（再帰的な枝分かれ）、葉を板ポリにした。ブランチ `feat/fractal-trees`（`feat/dense-forest` から作成）
- `world/fractalTree.type.ts` / `fractalTree.constants.ts`（針葉樹・広葉樹・細長い木の 3 種のパラメータ）、`world/fractalTreeModels.utils.ts`（骨格の再帰生成 → 枝と葉をそれぞれ 1 つのジオメトリにまとめる）、`world/leafTexture.utils.ts`（葉の画像を Canvas 2D で描く。画像ファイルは不要）
- 岩は `world/primitiveRockModels.utils.ts`（旧 `primitivePropModels.utils.ts` から木を除いた物）
- 種類ごとに 2 つの形を作る（モデル番号 = 種類 × 2 + 形。木の variantWeights は 6 件）
- 葉は向きを固定した板（ビルボードではない）。`alphaTest` + `alphaToCoverage`、両面描画。法線は樹冠の中心から外向き（少し上寄り）にそろえ、裏面で法線を反転しないよう normal_fragment_begin の後で戻している
- 全高は種類ごとに 6.2〜6.5m にそろえる（生成後に拡大縮小）
- 結果: 1 本あたり 約 360〜850 ポリゴン、同時描画 約 36 万ポリゴン、Draw Call 16。GPU（Apple M4 Pro）のヘッドレス Chrome で 60fps（最も遅いフレーム 16.8ms）
- 気になる点: 葉の板を真横から見ると線のように見えることがある。スマホでは未計測（Phase 8 で品質 tier・遠景の簡略化を検討）
- 計測のヒント: ヘッドレス Chrome は `--use-angle=metal --enable-gpu --ignore-gpu-blocklist` にすると GPU で描ける（SwiftShader の FPS は実機の目安にならない）

## 高く密な森（フラクタルの木の後の調整）

- ユーザーの要望で、木を高く・ボリュームを大きくし、密度を上げ、道に近づけた。軽くするため木は 1 種類（広葉樹）× 2 つの形にした（ブランチ `feat/tall-canopy`）
  - 木: モデルの高さ 9.5m、拡大率 0.85〜1.2 × 縦だけの伸び 0.9〜1.15（`heightScale` を配置データに追加）で 約 7.3〜13.1m。樹冠の幅 約 10m
  - 道との距離: 幹の中心を道の中心から 2.0m（以前は 3.5m）。枝は幹の上側 2 節からだけ出し、葉は `canopyMinHeight`（3.4m）より下に垂れる板を付けない。拡大率が最小でも葉の下端は 約 2.6m で、道の上に枝葉が張り出すトンネル状になる
  - 密度: 道の縁 0.55、8m で 0.75、12m 以遠 0.85。空き地の間引き 0.4。配置する最大距離を 42m → 36m（霧でほぼ見えないため）
  - 針葉樹・細長い木と、針葉樹の葉の画像は削除した（戻すときは b7b8a45 を参照）
  - 結果: 1 本あたり 約 710〜790 ポリゴン、同時描画 約 31 万ポリゴン、Draw Call 8、GPU（M4 Pro）で 60fps
- 高さの制限（約 9.9m 未満）を外した。新しいチャンクは 45m 先から入り、地平線より上に頭を出す木（7.3m 以上）は目から 47.5m 以上離れて霧で見えない。高い木ほど遠くなるので、高さで突然現れることはない（CLAUDE.md に前提を記載）

## Phase 4 で作ったもの（無限ループの検証）

- 円環座標・原点での折り返し・チャンクの mod 列挙・周期ノイズは Phase 1〜3 で実装済みだったため、Phase 4 はデバッグ機能の追加と境界の検証だけを行った。ループまわりの不具合は見つからず、描画側のコードは変えていない
- `ScrollController.teleport(distance)`: 慣性を付けずに進行距離を直接動かす（デバッグ GUI のループ検証用。NaN・Infinity は例外）
- `ScrollController.setAutoWalkSpeed(speed)`: 一定の速度で進み続ける（デバッグ GUI の自動歩行用）。update(dt) の中で目標位置と現在位置を同じだけ進めるため、velocity にもその速度が出て、入力による移動はその上に足される
- デバッグ GUI（`debug/Debug.ts`）
  - Status に `lap`（周回数。0m を前進でまたぐと +1、後退でまたぐと -1）を追加
  - Loop フォルダ: `jump s (m)` + `jump to s`（周回数はそのままコース s だけ移動。初期値 95m、刻み 0.01m、上限 99.99m）、`+10 laps` / `-10 laps` / `+10000 laps`、`auto walk (m/s)`（慣性なしで一定速度で進む。0 で停止）
  - 周回数は Debug の中で `Math.floor(distance / COURSE_LENGTH)`（`toLap`）から求める。Experience から渡す値（`IDebugReadouts`）は変えていない
- コードレビュー後のリファクタリング: 最初は Debug が毎フレーム `teleport` を呼んで自動歩行していたが、速度表示が 0 になり、ホイール入力も上書きされて効かなかったため、`setAutoWalkSpeed` に置き換えた。あわせて周回数の計算を `toLap` にまとめ、表示用の型（`IDebugStatus`）を受け取る型（`IDebugReadouts`）と分けた
- 検証結果（ヘッドレス Chrome・GPU（Apple M4 Pro）、1280×720、CDP で操作）
  - 0.1m 離れた 2 位置の画像の差（平均絶対差）: 境界 99.9→0.0m で 8.36、99.95→0.05m で 8.38。コースの途中（30→30.1m: 7.80、49.9→50.0m: 8.53、チャンク境界 74.9→75.0m: 8.24）と同程度で、境界だけ飛ぶことはない
  - 同じコース s（97m）で周回数だけ変えた画像（+10 周、+10010 周 = 進行距離 約 100 万 m、+9990 周）は、元の画像と画素単位で完全に一致した（数値誤差の蓄積なし）
  - ホイール入力で 95m → 5.5m（0m を前進でまたぐ、lap +1）→ 95m（後退でまたぐ、lap -1）を往復。ページの scrollTop は 0 のまま
  - 自動歩行 8m/s で 130 秒（約 1,050m = 10.5 周）連続で進み、フレーム間隔は平均 16.67ms・最大 16.8ms。歩いた後に 97m へ戻った画像も最初と完全に一致した
  - コンソールのエラーは favicon.ico の 404 のみ（`public/` がないため。Phase 4 とは無関係）
- ユーザーの確認: 2026-10-13 に動作を見てもらい、問題なしと判断された。実機のトラックパッド・タッチ・144Hz モニタでの確認は、計測上は未実施
- 開発サーバーを長く動かしていると、`?debug` で lil-gui の動的 import が `504 (Outdated Optimize Dep)` で失敗することがある。`pnpm exec astro dev stop` → `pnpm dev` で直る

## Phase 5 で作ったもの（オーブ）

- オーブは **10m 間隔で 10 個**（2026-10-13 にユーザーが決定。計画書の付録 B-12）。s = 5, 15, …, 95m、道の中心から左右交互に 0.8m（0 番目が左）、地面から 1.2m
- `src/data/orb.type.ts`（`TOrbId` / `IOrbContent` / `TOrbMarker`）、`src/data/orbs.data.ts`（`ORB_CONTENTS`。仮データ 10 件、色だけ 5 色を交互に）
- `procedural/orbSlot.*`: オーブの位置（`listOrbSlots`）と、配置物の除外判定（`isNearOrbSlot`）。Three.js 非依存。`ORB_SPACING` は COURSE_LENGTH を割り切るか起動時に検証する
- `placement.utils.ts`: オーブの周り（半径 `ORB_CLEARANCE` 1m + 配置物の clearance）に木・岩を置かない（Phase 3 の TODO を解消）。森の配置はそのぶん少し変わった
- `curvature/curvature.utils.ts`: TS 版の `curvaturePosition`（`curvature.glsl` と同じ式）。折り返しは既存の `wrapSignedCourse` を使う
- `orbs/OrbManager.ts`
  - 1 個ずつの Mesh（本体の球 半径 0.25m + 半透明の殻 0.42m + 判定用の見えない球 0.5m）。MeshBasicMaterial で光の影響を受けない（霧は掛かる）
  - 毎フレーム、共有 uniform（カメラのコース位置・惑星半径）から位置を CPU で求める。浮遊は ±0.12m・周期 3 秒、並び順で位相をずらす（経過時間ベース）
  - 描画範囲は前方 45m・後方 10m。目から 1.5m 以内で縮め始め、0.6m で 0 にする（すれ違うときの最接近は 約 0.9m）
  - クリック: 押してから 6px 未満・400ms 未満で離したときだけ。判定は表示中の判定用の球だけ、40m まで。当たったら `forest:orb-select`
  - ホバー: マウスのときだけ、毎フレーム 1 回判定し、カーソルを pointer にして少し大きく・白く

## オーブの見た目の試作（魂の炎）

- 2026-10-13 にユーザーと方向性を決定: オーブを「鬱蒼とした森に浮かぶ魂（人魂のような炎）」にする。参考はユーザーが貼った青白い炎のイラスト（白い芯 → 水色 → 濃い青の縁、上へ伸びる 2〜3 本の舌）

- ブランチ `feat/orb-soul-flame`（`feat/phase-5-orbs` から作成）。2026-10-13 にユーザーの確認を経てコミット済み
- `shaders/orbFlame.vert.glsl` / `orbFlame.frag.glsl`: 形は「火の玉の半径 = 1」の単位で描く。下は円・上はしずく形に細くなる輪郭を、上へ流れる fbm で横に揺らし、縁をノイズで崩し、上ほどノイズで削って舌に分ける。色は輪郭からの深さで「濃い色（指定色の 2 乗）→ 指定色 → 火の玉の中だけ白」。加算合成で、霧は色を混ぜず距離で明るさを落とす。板の端は UV でフェードする
  - 板の四角い輪郭が見える問題（ユーザー指摘）: 火の玉の周りの淡い光（指数関数で減衰）が板の端でも 0 にならず、わずかな値でも sRGB へ変換すると持ち上がって四角く浮き出ていた。中心から半径の 1.2〜2.0 倍で滑らかに 0 にし、板（±2.2）の内側で必ず消えるようにした。シェーダーに新しい光の項を足すときも、板の内側で 0 になるようにすること
  - それでも輪郭がうっすら残った（ユーザー指摘）。原因は標準の AdditiveBlending がアルファも足すこと。葉は alphaToCoverage で縁のアルファが 1 未満になっており、炎が 0 の部分でも板の範囲だけアルファが 1 に変わって葉の縁の見え方が変わっていた（炎の出力を 0 にしても、板の範囲の葉の縁だけ 1.5 万画素が変わることで確認）。CustomBlending で色だけを足し、アルファは描画先のまま残すようにして、差は 0 画素になった。加算合成のマテリアルを増やすときも同じ設定にすること
- `orbs/orbFlame.utils.ts`: 板のジオメトリ（火の玉の半径 0.24m、炎の全高 約 1.25m。ユーザーの要望で最初の 0.16m から 1.5 倍にした）、共有 uniform（時間・火の玉の半径）、オーブごとのマテリアル（色・個体差の種・明るさ）

- 霧: マテリアルを `fog: true` にし、three.js 標準の霧の uniform（`fogNear` / `fogFar`）を描画のたびに入れてもらう。デバッグ GUI で霧を変えると炎の消え方も追従する
- コードレビュー後のリファクタリング（`develop...feat/orb-soul-flame` を対象）
  - 霧の距離を OrbManager が毎フレーム手で写していたのをやめ、上記の three.js 標準の仕組みに任せた（OrbManager は霧を受け取らない）
  - 地面と炎で重複していたハッシュ関数を `shaders/hash.glsl`（`forestHash12`）にまとめ、両方のシェーダーの前に連結する。地面の見た目は画素単位で変わらないことを確認した

  - 浮遊の位相と炎のノイズの種を 1 つ（`variation`、黄金角 × 並び順）にまとめた。炎の揺らぎ方の模様はオーブごとに少し変わった
  - Phase 7 の TODO を OrbManager のクラスの説明へ移した

## Phase 7 の進め方

2026-10-13 にユーザーと決めた。計画書 §23 の Phase 7 の項目を 5 つに分け、区切りごとにユーザーに見てもらう。

1. オーブの光: Bloom、HDR の発光、炎の周りの光の粒（と、任意で最寄りのオーブ 1 個の PointLight）
2. 森の空気感: 木漏れ日の地面模様、光芒カード、浮遊粒子、ブロブ影（**実装済み・コミット済み**）
3. 色調: トーンマッピング（ACES / AgX を GUI で比較）、光・霧・空の色、任意でビネット
4. カメラと歩く感覚: 道の蛇行（振幅 1〜1.5m）、歩行の揺れ、マウス視差、`prefers-reduced-motion`
5. 読み込みのフェードイン

ユーザーへの説明で勧めた順番は「色調の土台（1・3）→ 2 → 4 → 5」だったが、ユーザーの指示で 2 から始めた。後で Bloom・トーンマッピングを入れると明るさが変わるため、2 の明るさ（光芒・粒子・斑点の強さ）はそのときに合わせ直す。

## 計画の核心（ここだけ押さえれば方針がぶれない）

- **惑星は擬似球面**: カメラは原点（球の頂上）に固定し、頂点シェーダーで世界を球面へ曲げる（`θ = 弧長 / R` の正確な球面写像）。見た目の半径 R（63.7m）とコース長 L（100m。Phase 1 の後に 400m から変更）は独立
- **ループ**: 全オブジェクトをコース座標 s ∈ [0, 100) で定義する。進んだ距離はリセットせず増やし続け、描画のときだけ `curvatureWrapSigned(s - cameraS)`（GLSL）で ±50m に折り返す
- **継ぎ目対策**: 地形・道の蛇行・密度ノイズは 100m で一周する関数で作り、乱数のセル番号を mod で折り返す。テクスチャのタイル幅は 100 を割り切る値にする。光と霧はカメラ相対
- **描画**: 木などは InstancedMesh（種類 × マテリアルごと）を使い、10m チャンク単位で可視ウィンドウを詰め直す。リアルタイムの影は使わない
- **オーブ**: 個別の Mesh で、TS 版の曲げ変換で位置を計算し、Raycaster で判定する
- **モーダル**: `<dialog>` を使う。`forest:orb-select` / `forest:modal-change` の CustomEvent で Three.js とつなぐ
- **依存**: 追加するのは `three` と `@types/three` のみ。レンダラーは WebGLRenderer（WebGPU は使わない）
